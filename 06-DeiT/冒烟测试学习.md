# 冒烟测试学习 —— 最小测试数据是怎么"编造"出来的

> 目标：讲清楚 `_check_user_files.py` 这个检查文件里**每一行断言的依据是什么**，
> 以及将来你怎么给自己的新模块设计同类测试。
> 名词来源：工程里"冒烟测试（smoke test）"= 通电看冒不冒烟，只验证"通路通不通"，
> 不验证"产品好不好"。

---

## 1. 核心思想：测契约，不测效果

冒烟测试和"跑 1 个 epoch 看精度"是两回事：

| | 冒烟测试 | 小规模真实训练 |
|---|---|---|
| 数据 | **编造的随机张量** | 真数据（CIFAR-100） |
| 目的 | 代码通路对不对、接口接没接对 | 模型学不学得会 |
| 时间 | 秒级 | 分钟~小时级 |
| 能抓的 bug | 形状错、参数漏建、分支没写、梯度断流 | 精度不涨、发散、过拟合 |

**为什么随机张量就够？** 因为模型代码的正确性不依赖数据的"内容"，只依赖数据的
**形状、类型、设备、数值范围**。`x = torch.randn(2,3,32,32)` 和一张真的猫图，会走
**完全相同**的几十行代码——如果随机张量能通过，真图也一定能通过（反过来不一定，但那是
"效果问题"，归真训练管）。

## 2. 我的检查文件里，每条断言依据什么

以 `_check_user_files.py` 为例，逐条拆解"编造依据"：

### ① 参数量 ≈ 5.4M（配置级 sanity check）

```python
m = DistilledVit()
print(sum(p.numel() for p in m.parameters()) / 1e6)
```

依据：**论文规格表**。DeiT-Ti = embed 192 × 12 层 ≈ 5.3~5.4M。如果打印出来是 0.5M 或
50M，说明 `__init__` 里参数漏建/重复建了——**用"外部已知事实"当第一道闸门**，不用懂
内部实现就能抓错。

### ② 输入用 `(B=2, 3, 32, 32)` 的随机张量

依据：**形状从真实管道倒推**。CIFAR 图 = 3 通道 × 32×32；B=2 是"最小但有意义"的批大小
（B≥2 才能触发 batch 维的广播、expand、mean 等路径；B=1 有时会掩盖 batch 相关的错误）。
数值用 `randn` 而不是真图：因为这里要检查的是**形状契约**，不是语义。

> 最小性很重要：B=2 一个 forward 只要几毫秒；真数据要下载 169MB + 50 万张图，慢四个数量级。

### ③ 训练模式输出 `(2,100)+(2,100)`，eval 模式输出 `(2,100)`

依据：**论文定义的接口契约**。DeiT 论文 Sec 3.2 + 官方实现约定：
- 训练时：两个头**分别**输出（一个学真值、一个学教师）→ 元组；
- 推理时：双头**平均**成一个 → 单张量。

冒烟测试就是把这两条"你和我口头约定的契约"变成**代码断言**，防止将来谁改了 forward
的返回格式，训练循环在不知情的情况下崩掉。

### ④ backward 不炸（梯度流检查）

```python
(out[0].sum() + out[1].sum()).backward()
```

依据：反向传播是"全链路"检查——任何一层没接进计算图、任何 in-place 操作破坏了梯度，
都会在这里暴露。这一行抓过的最典型 bug：`pos_embed` 长度对不上、forward 返回 None 等
**前向能跑、反向才炸**的问题。

### ⑤ 无蒸馏分支 `distilled=False`

依据：**分支覆盖**。`if self.distilled:` 两条路都要走一遍——只测默认配置会漏掉
else 分支的 bug（上次真抓到一个：无蒸馏时 pos_embed 长度 66 vs 序列 65，直接崩）。

### ⑥ loss 初始值 ≈ ln100 ≈ 4.6（量级检查）

```python
total, base, dist = distillation_loss((sl, dl), tl, y, args_h)
print(total.item())   # 期望 ~4.6
```

依据：**数学推导**。随机初始化的 logits 接近均匀分布，softmax 后每类概率 ≈ 1/100，
交叉熵 = −Σ(1/C)·ln(1/C) = **ln C**。所以：
- 打印值在 4.6 附近 → loss 公式没写错（没有忘除批大小、没有用错 log 底数）；
- 打印值是 0 或 46 → 必有 bug（比如把 softmax 后的概率又取了一次 log）。

这就是"编造数据 + 数学期望"的组合拳：**输入随便造，但输出必须命中数学算出来的靶心**。

### ⑦ smoothing=0 时与 `F.cross_entropy` 完全相等（等价性检查）

依据：**用可信参考实现当裁判**。你的 `soft_cross_entropy` 是自己推的公式，怎么证明它对？
让它在 smoothing=0 时退化成标准 CE，然后和 torch 官方实现逐位比较——
实测 `5.0347 == 5.0347`，你的平滑公式就拿到了"官方认证"。

> 一般化原则：**永远不要用"自己的理解"验证"自己的代码"**，要找第三方裁判——
> torch 官方函数、论文报告的已知数值、另一个已跑通的实现，都行。

### ⑧ hard / soft 两个分支都跑 + 都 backward

依据：**分支覆盖 ×2**。硬蒸馏和软蒸馏是两条独立代码路径，只测一条会漏另一条的
（上次的教训：软蒸馏的温度 `tempetature` 拼写，就是跑 soft 分支时暴露的）。

### ⑨ 2D 软标签分支

依据：**为未来铺路**。v2 上 Mixup 时 targets 会变成 (B, C) 的软标签而不是 (B,) 索引，
现在就把这条路径测了，v2 加 Mixup 时少踩一个坑。

## 3. 一般化方法：怎么给自己的新模块设计冒烟测试（四步法）

1. **列契约**：这个模块的输入/输出形状是什么？训练/推理行为有何不同？有几个分支？
   （先想，再写测试）
2. **编最小输入**：形状照真实管道抄，数值用 `randn`/`randint`，批大小取 2~4；
3. **定数学期望**：输出的数值必须落在数学算出来的区间（loss ≈ ln C、softmax 行和为 1、
   概率在 [0,1] 等）；
4. **找裁判**：等价路径和 torch 官方实现比（`F.cross_entropy`、`nn.CrossEntropyLoss` 等）。

## 4. 实战战果：这套测试在本项目真实抓到过的 bug

| bug | 怎么抓到的 |
|---|---|
| `nn.ModuleList` 不可调用（`self.blocks(x)` 崩） | ②+③ 一跑就崩 |
| 无蒸馏时 pos_embed 长度不匹配（66 vs 65） | ⑤ 分支覆盖 |
| `TF.affine` 缺 `shear` 参数（torchvision 版本差异） | ② 走增强管道 |
| 无蒸馏 forward 返回元组导致 loss 崩 | ③ 契约断言 |
| 软蒸馏 `tempetature` 拼写错 | ⑧ soft 分支 |
| 标签平滑公式推导错误 | ⑦ 等价性检查（这是最隐蔽的，不改也能跑，但 loss 恒错一点点） |

**结论：假数据真的能抓真 bug**——而且比真数据快四个数量级。

## 6. 冒烟测试测不到什么（边界）

- **测不到精度**：随机数据上学不出"猫和狗"；
- **测不到收敛性**：1 个 batch 的 loss 下降说明不了训练会成功；
- **测不到数据问题**：真实数据集的脏样本、类别不平衡、增强管道的语义正确性。

所以流程永远是：**冒烟测试（秒级，抓接线错误）→ 小规模真训练 1 epoch（分钟级，抓
训练循环问题）→ 完整训练（小时级，看精度）**。三层递进，每一层只解决自己的问题。
